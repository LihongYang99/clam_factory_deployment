Normal measurement frames continued to pass validation. An earlier session
reported a first-point ACK, so previous coefficients must not be assumed intact.

After an ESP32 restart (boot ID changed from `7841a387d14f248d` to

uptime 220843 ms. Restarting the ESP32 did not resolve the response; these
logs do not independently establish whether the probe's power was cycled.
No further write retries are planned on the same evidence.

## Frame checks

| Frame | Bytes (hex) | Evidence |
| --- | --- | --- |
| Point 1, 200 mV request | `01 10 01 20 00 02 04 00 01 00 C8 AC 71` | Generated by local code; not captured independently on the RS485 bus |
| Point 2, 600 mV request | `01 10 01 20 00 02 04 00 02 02 58 5D 7D` | Generated by local code; not evidence of a successful second write |
| Documented success response | `01 10 01 20 00 02 41 FE` | DFRobot protocol example |
| Actual point-1 response | `01 90 01 20 00 01 00 21` | User's serial log; CRC is valid |

The request builder matches DFRobot's documented register layout and byte order.
CRC checks were independently recomputed. The response has function 0x90 instead
of 0x10 and a different payload. It is not the documented ACK. It is also not a
standard five-byte Modbus RTU exception; its remaining bytes cannot be assigned
a standard exception meaning without manufacturer documentation. The exact
captured response is covered by a regression test and must remain unconfirmed.

## Conflicting calibration instructions

The [DFRobot SEN0709 guide](https://wiki.dfrobot.com/sen0709/docs/23380) specifies
the lower standard first, then the higher standard. Its
[protocol examples](https://wiki.dfrobot.com/sen0709/docs/23382) use 86 then 256 mV.
The firmware follows that order with fixed targets of 200 then 600 mV.

A [Renke RS-ORP-N01-3 manual](https://save.jnrsmcu.com/产品使用说明书/普通型产品/水产水质/RS-ORP-N01-3一体式ORP变送器485型说明书.pdf),
retrieved as V1.4, uses the same calibration register layout but explicitly requires
the higher point first (section 2.3.5, page 10). Its version history says V1.2
corrected the two-point calibration description (page 13).

This is a lead for checking a documentation or device-version mismatch, **not
proof that SEN0709 is that model or that reversing the order fixes this reply**.
Neither source inspected explains the captured eight-byte 0x90 response.

## DFRobot-only review

The operator selected 200 then 600 mV. Keep that order: the SEN0709 guide
explicitly specifies lower then higher. Its 86/256 mV pair is an example,
not an expressly stated restriction to those two values.

The published protocol has no separate enter-calibration or save command.
`CAL BEGIN` is our ESP32 command: it pauses MQTT telemetry and enables manual
writes; it sends nothing to the probe. Likewise, `calibration_status` is a
hard-coded project label, not a status read from the sensor. A successful
write would still require verification and a recorded calibration result.

The [official Arduino example](https://wiki.dfrobot.com/sen0709/docs/23381)
only reads ORP/temperature; it does not provide a calibration implementation
or decode this response. The [official troubleshooting FAQ](https://www.dfrobot.com/forum/topic/401053)
requires polling and response-wait settings above 200 ms. Our normal poll is
5000 ms and timeout is 1000 ms, with a 20 ms quiet gap ending a received frame.
However, manual writes and normal reads have no separate minimum transaction
spacing. This should be checked before further writes; it is not a demonstrated
cause. A response received in 47 ms is not itself a timeout.

The reference exposes readable offset/slope registers, but no documented
calibration-state register. A read-only diagnostic can record current coefficients;
without earlier values it cannot prove whether a previous write changed them.
The slope example also has an arithmetic typo: 293/309 is about 0.94822,
not 0.7735. Do not copy its coefficient as a correction for this probe.
